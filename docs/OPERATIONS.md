# OT Hub 운영 안내

## 현재 준비 상태

로컬 구현: 빠른 메뉴 전환, 반응형 UI, 검색, 저장/최근 이용, 기존 좋아요·댓글 연결, 업데이트 기록, 선택적 통계, 관리자 집계, DB 권한 검사, CI.

운영 미적용: 통계 SQL, 관리자 지정, 90일 삭제 작업, 수집 활성화, 실제 도메인 인증 리디렉션, 운영 배포. 홈페이지 탐색은 이 설정과 무관하게 작동합니다. 처음부터 가짜 통계나 실제 이용자 수처럼 보이는 숫자를 표시하지 않습니다.

## 배포 전 연결 순서

1. 기존 서비스와 DB 백업/복구 수단, 현재 배포 ID를 기록하고 스테이징에서 시작합니다.
2. Supabase SQL Editor에 `supabase/migrations/202609200001_usage_analytics.sql`을 적용합니다. 기존 `supabase/schema.sql`은 실제 운영 댓글 스키마와 다른 옛 설계이므로 실행하지 않습니다.
3. Supabase Auth에서 관리자 이메일이 기존 계정인지 확인합니다. 관리자의 UUID를 직접 확인한 후 아래 SQL의 자리표시자를 바꿔 SQL Editor에서 실행합니다. 브라우저에 service-role 키를 넣지 않습니다.

```sql
insert into public.othub_admins(user_id)
values ('REPLACE_WITH_VERIFIED_AUTH_USER_UUID')
on conflict do nothing;
```

4. Auth 허용 리디렉션에 실제 도메인의 `/index.html`과 `/admin.html`, 필요한 로컬/스테이징 주소를 등록합니다. `supabase-config.js`는 기존 프로젝트 URL과 공개 anon 키를 사용합니다.
5. pg_cron 확장을 켜고 `supabase/retention.sql`을 실행합니다. UTC 03:20에 90일이 지난 이벤트를 삭제합니다. `cron.job_run_details`에서 성공을 확인한 후 수집을 켭니다.
6. 스테이징에서 익명/일반 회원의 관리자 RPC 거부, 관리자 조회 허용, 원시 테이블 읽기 거부를 실제 Auth 토큰으로 확인합니다. 실제 이메일 로그인 및 기존 좋아요·댓글 읽기/쓰기/취소를 테스트 계정으로 검증합니다.
7. Supabase 수집 엔드포인트에 사용 가능한 네트워크/WAF 제한을 적용합니다. RPC에는 세션당 500건/시간, 전체 100,000건/UTC 일의 상한과 배치 최대 20건이 있습니다. **이것은 인증된 방문 증명이 아닙니다.** 익명 호출자가 세션 ID를 바꾸거나 이벤트를 조작할 수 있고, 전역 상한을 소진하면 정상 수집도 중단됩니다. 공개 유입이 커지면 IP 기반 제한을 가진 Edge Function을 앞에 두고 공개 RPC 실행권을 제거합니다. 요청 실패/메일 전송 남용도 함께 모니터링합니다.
8. 운영 주체·문의 주소·처리 업체·보관/삭제·이용 조건을 포함한 실제 개인정보처리방침과 이용약관을 확정합니다. 현재 화면의 데이터 안내는 선택적 통계 기능의 범위 설명이며 전체 정책이 아닙니다.
9. 위 절차가 완료되면 `supabase-config.js`에 `window.OT_HUB_ANALYTICS_ENABLED = true;`를 추가합니다. 기본은 false입니다. 사용자도 `내 정보 → 서비스 개선 통계에 참여`를 선택해야 전송됩니다. DNT/GPC 활성 브라우저는 전송하지 않습니다.
10. 스테이징의 QA 통과 후 운영 배포하고 `assets/releases.js` 상태를 실제 배포 상태/일자로 바꿉니다. 운영 홈페이지, 로그인, 콘텐츠 링크, 통계 조회를 직접 확인합니다.

## 지표 읽는 법

| 지표 | 의미 | 주의점 |
|---|---|---|
| 방문 세션 | 30분 비활동 시 갱신되는 임의 세션 ID | 고유 인원·회원 수가 아님. 탭 복제 시 ID가 복사될 수 있음 |
| 메뉴 조회 | 동의 후 표시한 화면 | 재방문·새로고침 포함 |
| 콘텐츠 열기 | 홈페이지에서 콘텐츠 링크 클릭 | 게임 로딩 성공·훈련 완료와 다름 |
| 전환 시간 p75 | JS 전환 시작부터 두 번째 애니메이션 프레임까지 | 실제 INP 아님. 60,000ms 상한, 백그라운드 측정은 부정확할 수 있음 |
| 메뉴 이동 흐름 | 수집된 같은 세션의 연속 화면 | 동의 전 이동·전송 유실 구간은 알 수 없음 |
| 검색 / 결과 없음 | 검색 결과 건수 | 검색어는 수집하지 않음 |
| 유입 유형 | referrer를 검색/소셜/기타/직접으로 분류 | URL·검색 파라미터·상세 유입 캠페인은 저장하지 않음 |
| 기기 | 화면 너비로 모바일/태블릿/데스크톱 분류 | 같은 방문이 너비 변경 시 둘 이상에 집계 가능 |

모든 기간과 일별 집계는 UTC 기준입니다. 동의한 표본에 한정하므로 전체 사용자 규모나 성과로 단정하지 않습니다. 전송 실패는 메모리 내 최대 50건으로 제한하며 페이지를 닫으면 유실될 수 있습니다. 중복 이벤트 ID는 서버에서 제외합니다. 동의 철회 후 대기열을 비우고 추가 요청을 막지만 이미 완료되었거나 전송 중인 요청을 취소·삭제하지는 않습니다.

## 운영 일정

- 매주 월요일: 지난 7일 콘텐츠 열기, 메뉴 이동, 결과 없는 검색, 클라이언트 오류, 전환 지연을 확인하고 상위 3개 개선 항목만 선정합니다.
- 매주 금요일: 수정 PR, 테스트 결과, 모바일 화면, 실제 게임 링크를 검토합니다. 작은 버그 수정은 검증 후 패치 버전으로 배포합니다.
- 매월 첫 주: 기능 업데이트를 묶어서 배포합니다. 변경 기록·스크린샷·복구 배포 ID를 남깁니다.
- 매월: 의존성 업데이트, DB 저장량/비용, 삭제 작업 성공, 관리자 계정 목록, 로그인 메일 도달 여부를 확인합니다.

이 일정은 운영 계획이며 자동 예약이나 알림을 생성하지 않았습니다.

## 배포 검증과 복구

`npm run check`, `npm run test:db`, `npm test` 통과 후 리뷰합니다. CI의 스크린샷과 navigation.json을 이전 릴리스와 비교합니다. 네트워크가 느리거나 로그인 서버가 실패해도 콘텐츠 탐색이 되는지 확인합니다. 게임의 카메라·오디오·터치 사용성은 실제 기기에서 별도 확인합니다.

이상이 생기면 먼저 수집 플래그를 false로 배포해 통계를 끄거나 Vercel의 직전 정상 배포로 롤백합니다. 게임 HTML 경로는 유지되어 기존 직접 링크가 계속 동작합니다. 이번 DB 변경은 별도 테이블/RPC 추가이므로 앱 롤백에 테이블 삭제가 필요하지 않습니다. 관리자 권한 회수는 아래와 같습니다.

```sql
delete from public.othub_admins
where user_id = 'REPLACE_WITH_VERIFIED_AUTH_USER_UUID';
```

## 보안·성능 근거

집계 접근은 브라우저 버튼 노출이 아니라 DB의 `auth.uid()`와 관리자 테이블로 검증하며, security-definer 함수에는 빈 search_path와 명시적 스키마를 사용합니다. [Supabase 함수 문서](https://supabase.com/docs/guides/database/functions), [RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security).

실사용 반응성 목표는 p75 INP 200ms 이하로 잡되, 현재 구현의 전환 프레임 시간과 별도로 출시 후 실사용 계측을 검토합니다. [web.dev INP](https://web.dev/articles/optimize-inp).
