# 개인 프로젝트에서 공개 SaaS로

목표는 사용자가 필요한 활동을 빠르게 찾고, 운영자는 사용 흐름을 근거로 꾸준히 개선할 수 있는 서비스입니다. 현재 콘텐츠 중심의 정적 구조를 유지하고 병목을 분리했습니다. 당장 프레임워크와 DB 전체를 교체할 이유는 없습니다.

## 1차 구현 — 이번 변경

- 큰 인라인 HTML에서 이미지·데이터·화면·인증·통계 분리
- 정적 메뉴 화면의 DOM 캐시, 일관된 메뉴 상태/뒤로 가기/직접 링크
- 로그인·통계와 독립적으로 즉시 탐색, 검색 입력 병합 처리
- 동일한 색상·여백·카드·타이포그래피의 반응형 UI
- 이 기기의 북마크·최근 이용, 기존 공개 콘텐츠와 좋아요·댓글 유지
- 준비되지 않은 임상 도구·커뮤니티·가짜 조회 수를 주요 탐색에서 제거
- 실제 데이터만 표시하는 운영 화면, SQL 권한/집계 검증
- 버전별 업데이트 기록, 배포 준비 상태, 회귀 검사와 CI

## 이후 6주 권장 순서

| 시기 | 작업 | 완료 기준 |
|---|---|---|
| 1주차 | 스테이징, 통계 DB, 운영 계정, 동의/정책, 실제 메일 로그인 | 익명/일반/관리자 역할별 검증, 실제 도메인에서 로그인 및 집계 성공 |
| 2주차 | 제한된 공개 운영, 기기별 이용 관찰, 오류 수정 | 모바일 주요 활동 접근과 실행 확인, 오류와 지연의 기준값 확보 |
| 3–4주차 | 실제 이용 상위 콘텐츠 개선, 링크 검증, 피드백 수집 흐름 | 주간 상위 불편 3건 해결, 릴리스 기록, 접근성 수동 검사 |
| 5–6주차 | 콘텐츠 등록/검토/게시 관리, 회원 저장 동기화 필요성 결정 | 콘텐츠 게시에 대한 작성자/검토자/게시 상태 모델 확정 |

기간은 제안이며 확정 일정이나 자동 실행 예약이 아닙니다. 정규 업데이트는 매월 첫 주, 버그 수정은 검증된 패치 단위로 운영합니다.

## 출시 체크포인트

- [ ] 실제 운영 도메인과 기존 배포/복구 버전 확인
- [ ] 관리자 이메일/계정 지정 및 스테이징 통합 테스트
- [ ] 데이터 삭제 작업·수집 제한·운영 비용 한도 확인
- [ ] 개인정보처리방침/이용약관/문의 창구 확정
- [ ] 실제 Android/iOS, 키보드/스크린리더에서 주요 흐름 확인
- [ ] 주요 훈련 앱의 카메라·오디오·결과 화면 수동 확인
- [ ] 공개 배포 후 소수 사용자와 관찰, 개선 우선순위 재정렬

## 업데이트 운영 원칙

패치 `0.2.x`는 오류 수정과 작은 UX 개선, 마이너 `0.3.0`은 기능 추가, `1.0.0`은 공개 운영 요건을 충족했을 때 사용합니다. 버전 문자열은 package.json, releases.js, analytics.js, 화면 footer를 함께 갱신합니다. 공개 변경 기록에는 기능과 실제 배포일만 쓰고 미완료 기능은 계획으로 구분합니다.

매월 업데이트는 ‘불편 확인 → 3개 내외 우선순위 → 구현 → 자동 검사/실기기 확인 → 스테이징 → 운영 배포 → 지표 확인’으로 반복합니다. 기능 추가 수보다 메뉴 반응성, 실패율, 결과 없는 검색의 감소를 우선합니다.

회원 규모, 동시 접속, 비용의 현재 값이 없으므로 매출·전환율 목표는 임의로 설정하지 않습니다. 2주 이상 관찰한 후 기준을 정합니다. 결제·유료 구독·기관별 권한·환자 데이터 저장은 별도 제품 결정과 데이터 설계가 필요하며 지금 코드에서 제공한다고 표시하지 않습니다.

## 장기 관리에서 남은 기술 과제

통계의 IP 제한을 위한 Edge 수집 API, 상세 모니터링과 INP/LCP 실사용 계측, 스테이징/운영 분리, Supabase 메일/권한 감사, 관리자 콘텐츠 편집, 실제 브라우저 지원 범위와 접근성 기준, 해시 라우팅을 대체할 URL 체계 필요성 검토. 트래픽이 증가하면 현재 전체 기간 집계 RPC를 일별 집계 테이블로 전환합니다.

기존 훈련 HTML은 이번에 내부 구조를 재작성하지 않았습니다. 공유 게임 셸, 훈련 시작/완료 이벤트, 오류 복구와 테스트를 게임 단위로 순차 적용합니다. 훈련 기록이나 건강 정보를 수집하려면 현재의 익명 이용 통계와 분리된 설계를 먼저 확정합니다.
